# Payment picker

Customers choose how they want to pay **on Umzila's checkout page** (Card, Capitec Pay, Instant EFT, Apple Pay / Google Pay / Samsung Pay on devices that support them, or "More ways to pay"), and PayFast opens directly on that method. Before this, every buyer landed on PayFast's full method list and had to choose there — one extra screen and decision on somebody else's site. The payment itself still happens on PayFast (redirect integration); nothing is embedded, and signing stays on the server.

Everything is behind one master switch: `site_settings` key `payments` → `enabled` (**Admin → Payments → Payment options → "Payment picker on"**). **While it is false the whole system is inert**: checkout renders today's payment panel and calls `generate-payfast-signature` directly exactly as before, `begin-payment` refuses with `PICKER_OFF`, the ITN skips the server confirmation, and no attempt rows are written. Design: `docs/plans/payment-picker-checkout-plan.md` (its §0 FOUNDER DECISIONS override the founder's brief and the mockups); brief: "Umzila payment method picker developer brief" (2026-11-14, rules P1–P18). Built 2026-11-15 by four workstreams (A database + server, B checkout.html, C admin, D success/cancel pages + docs + QA), reviewed and fixed the same day (migration `pp_payment_picker_review_fixes`, `docs/plans/sql/8_pp_payment_picker_review_fixes.sql`; see the CHANGELOG entry).

## What the customer sees, end to end
1. Checkout loads the option list (one anon read of `site_settings.payments`). Step 4 "How do you want to pay?" shows one row per option that is **on** and **allowed on this device**, in admin order. A first-time buyer has nothing selected. A returning buyer has their last *paid* option preselected — but only if that option is still on and allowed on this device; otherwise nothing is selected.
2. Picking **Card** opens the card sub-picker inside the row: the buyer's saved cards (`payment_methods`, charged in one tap through `charge-payfast-token.js`, no PayFast page) and "Add a new card" (PayFast `cc`, with the existing "Save this card" switch + nickname). Every other option is a plain row.
3. The Pay button names the choice: "Pay R210 with Capitec Pay", "with card", "with <saved-card nickname>", "on PayFast" for More ways to pay. The delivery promise sits in the line above it ("Today, dispatched by 12:00") — customers are only ever promised the **dispatch** time, never an arrival window (founder decision 2026-11-15). Pay with nothing selected → "Choose how you want to pay" and the options card is outlined red; nothing is sent anywhere.
4. Pay → the browser makes (or reuses, see below) the `pending_payment` order exactly as today, then calls `begin-payment.js`, which records an attempt and returns the signed PayFast form. The browser posts it; PayFast opens on the chosen method.
5. Paid → PayFast's ITN confirms the order as it always has. `checkout-success.html` polls `order-status.js`, shows "Paid R210 with Capitec Pay" (`paidWith`), empties the cart (keeping `ss_cart_after_paid` lines) and forgets the pending order.
6. Cancelled on PayFast → PayFast's `cancel_url` is `checkout.html?pf=cancel&m_payment_id=…&attempt=…[&store=…]`. Checkout marks that attempt cancelled, shows "Payment not completed. Try again or choose another way to pay.", reopens Step 4 and restores the option and delivery time. Cart, details and address were never cleared. Paying again — with the same or another option — is a **new attempt on the same order**.

R0 orders (fully covered by a voucher/code) never see the picker: the button reads "Complete order" and `complete-zero-total-order.js` runs as before (P17).

## The pieces and how they connect

**Settings — `site_settings` key `payments`** (no new table; readable by everyone, admin-written, same pattern as `timeslots`): `enabled`, `no_answer_minutes` (default 30), `itn_validate` (default true), and `options[]` = `{ key, name, description, code, active, position, device }`. `key` is our own stable name (`card`, `capitec`, `eft`, `apple_pay`, `google_pay`, `samsung_pay`, `more`) — the browser only ever sends a key, never a PayFast code. `code` is one of PayFast's documented codes (`cc dc cp ef ap gp sp ss zp mp mc mt pf ab nd rc mu sc`) or `null` for the single catch-all. `device` is `null` (everyone), `'apple'`, `'android'` (Android incl. Samsung Internet) or `'samsung'` (Samsung Internet only). `key: 'card'` is special in the browser only (it shows the saved-card sub-picker); the server treats it like any `cc` option.

**`netlify/functions/begin-payment.js`** — the only entry point when the picker is on. It reads the settings, refuses anything that is not on the list and switched on (`OPTION_UNAVAILABLE`, P5 — never a silent fallback), loads the order by `m_payment_id`, checks identity from the Bearer token (guests: only orders with `user_id` null), re-runs the delivery-run check for a reused order via `payment_order_recheck` (P18), ignores a second tap within 8 s (`ATTEMPT_IN_FLIGHT`), inserts a `payment_attempts` row and writes `orders.payment_option_key / payment_method_code`. Then either it calls the existing `charge-payfast-token` handler in-process (saved card) or the existing `generate-payfast-signature` handler in-process with two **server-only** event fields, `trustedPaymentMethod` (the option's code, or nothing) and `trustedAttemptId` (→ `custom_str3`), and appends `&attempt=<id>` to the payload's `cancel_url` before signing. Neither PayFast function is called differently by anything else.

**`generate-payfast-signature.js` (additive only)** — `payment_method` is taken only from `event.trustedPaymentMethod`; a `payment_method` in the browser's payload is ignored on purpose, so today's direct callers produce byte-identical signatures. It is signed **after `confirmation_address` and before `subscription_type`** (PayFast's documented section order: merchant → customer → transaction → transaction options → payment method → recurring billing). Empty fields are left out of the string and the form, so "More ways to pay" sends no `payment_method` at all (P6). `custom_str3` = the attempt uuid (`custom_str1/2` remain seller enrolment / ad campaigns).

**`public.payment_attempts`** (the one new table; one row per Pay press, P8): order, `m_payment_id`, user, `option_key` (or `'legacy'`), `payment_method_code`, `kind` (`redirect` / `saved_card` / `zero`), saved card used, amount, `status` (`started → paid | cancelled | failed | no_answer | paid_twice | refunded`), times, PayFast's `pf_payment_id`, `amount_gross / amount_fee (stored positive) / amount_net` from the ITN, the extra payment's ITN for `paid_twice` rows, browser-reported device (display only), note. RLS: staff can read; nobody writes from a browser — only the service role and SECURITY DEFINER RPCs.

**`orders` columns (additive, nullable; server-owned — the BEFORE INSERT trigger `orders_payment_columns_guard` nulls all five on any anon/authenticated insert, and `orders_client_update_guard` already blocks client updates)**: `payment_option_key`, `payment_method_code` (`'token'` = saved card, `'zero'` = R0, null = picker off / before this build), `payment_flag` (`paid_twice` / `amount_mismatch`), `payment_flag_attempt_id`, `payment_flag_resolved_at`. Fee and net per paid order are read from `orders.pf_response` (the whole ITN, already stored for every ITN-paid order) — not copied into new columns. `orders_client_update_guard` already blocks browsers from writing them.

**ITN — `payfast-itn.js` + `lib/complete-order-payment.js` (additive)**. The order is still matched by `m_payment_id` exactly as before; the attempt is matched by `custom_str3` (P9). Only while the picker is on, after the signature check, the ITN is posted back to PayFast's `/eng/query/validate`: `VALID` continues, an explicit `INVALID` marks the attempt failed and does **not** complete the order, a timeout/network error (4 s) continues (the passphrase signature already passed; a hiccup at PayFast must never drop a real payment). Inside `completeOrderPayment` (shared by the ITN, saved cards and R0): **paid twice** — the order is already paid and this ITN carries a *different* `pf_payment_id` → the order is not touched, the extra payment goes on a `paid_twice` attempt row and the order is flagged (P13); the *same* ITN again changes nothing (the existing `alreadyPaid` guard). **Attempt confirmation** — the attempt in `custom_str3` becomes `paid` with PayFast's number and fee, and the order's option columns are confirmed from it (P14); this does not check the previous status, so a late success after "no answer" still confirms (brief edge case). **Amount check** — gross ≠ `orders.total` by more than 1c → flag `amount_mismatch` **and still complete**.

**No-answer sweep** — inside the existing once-a-minute `timeslot-tick` (`lib/timeslots.js runTick()`, before the timeslots switch is read): attempts still `started` after `no_answer_minutes` become `no_answer`. One idempotent statement; no new schedule.

**RPCs** — `my_last_payment_option()` (signed-in buyers: the option of their newest paid attempt — that *is* "saved on the account"; no profile column), `payment_attempt_cancelled(p_attempt, p_m_payment_id)` (anon OK: flips only a `started` attempt whose uuid + order reference match — a pair only the payer's browser and PayFast know), `payment_order_recheck(p_order_id)` (service role only), and the admin ones `admin_payment_report`, `admin_payment_flagged`, `admin_payment_resolve_flag`, `admin_paid_orders`, `admin_payment_attempts` (all check `timeslot_is_admin()`).

**`order-status.js`** — adds `paidWith: { option_key, name, amount_gross }` for paid orders (`name` from the settings; "Saved card" for `token`; null if unknown). `checkout-success.html` turns it into "Paid R210 with Capitec Pay" ("on PayFast" for `more`, lowercase "card" for the Card option).

**`checkout-cancel.html`** — no longer the normal cancel page. With the picker on, PayFast returns straight to checkout. The page stays for (1) checkout payments started before the deploy (`cancel_url = checkout-cancel.html?m_payment_id=UMZILA-…`): a head script immediately `location.replace`s them to `checkout.html?pf=cancel&m_payment_id=…[&attempt][&store]` (values validated, nothing else passed on); and (2) **seller enrolment** cancels (`initiate-seller-enrollment.js` sends `checkout-cancel.html` with no `m_payment_id`), which still see the "Payment not completed — no money was taken" card. Without JavaScript the card shows too.

## Browser storage
- `sessionStorage umz_pending_order = { m, orderId, fingerprint, slot_id, run_date, option_key, attempt_id }` — written by checkout after each order insert. On Pay, if the fingerprint (cart lines/qty/size/picks, total, code, email, phone, address, run, tip, priority, save-card) still matches, checkout **reuses that order** instead of inserting a new one (P11) — the server still re-checks the delivery run. A changed price changes the total and therefore the fingerprint, so a new order is made. Session storage = per tab, which is right: PayFast's cancel returns into the same tab. `checkout-success.html` removes it once the order is paid (only when its `m` is this order). A new tab simply makes a new order on Pay.
- `localStorage umz_pay_option` — guests' remembered option. Checkout writes it when it sends the buyer to PayFast (the only moment it knows the choice); `checkout-success.html` keeps it when the order is confirmed paid and removes it when polling gives up without seeing "paid" (the brief: remember after a *successful* payment). The success page accepts either a bare key or `{ key, m }`; a value tagged with another order is left alone. Signed-in buyers don't need it — `my_last_payment_option()` answers from paid attempts.

## Device rules
Checkout decides the device class once: `apple` when `window.ApplePaySession && ApplePaySession.canMakePayments()`, `samsung` for Samsung Internet, `android` for other Android browsers, else `desktop`. Apple Pay rows show only on `apple`, Google Pay on `android` or `samsung`, Samsung Pay on `samsung`. The device is also stored on the attempt (display only — never trusted for anything).

## Fallbacks (a fault in the picker must never stop a sale)
- Settings can't be read, or the picker is on but no visible option with a code is left → one preselected "Pay on PayFast" row (key `more`, no `payment_method`) (P15/P16). That row pays through today's direct signer (no attempt row, no `begin-payment`), so checkout never reuses a pending order on this path — a fresh insert runs the timeslot trigger (P18).
- `begin-payment` errors / network failure → "We could not reach PayFast. Check your connection and try again."; the attempt stays `started` until the sweep marks it `no_answer`.
- `OPTION_UNAVAILABLE` (admin switched it off mid-checkout) → checkout re-reads the list, clears the selection and says "That way to pay is not available right now. Choose another."
- `TIMESLOT_CLOSED` on a retry → the same handling as the order insert refusal: the next open run is selected and the buyer presses Pay again.
- `PICKER_OFF` / `ORDER_CLOSED` → "Please refresh checkout."

## Admin portal (Admin → Payments, `payments-admin.js`)
- **Payment options** — master switch "Payment picker on" (with a confirm), no-answer minutes, server-confirmation switch, the option list (reorder, on/off, edit name/description/device rule, add from PayFast's code list or the catch-all), a live "Customers will see …" line and PayFast's fees per method as help text. Switching an option off takes effect on the customer's next checkout load (and at once for anyone pressing Pay, because the server re-checks).
- **Flagged orders** — "Paid twice" / "Amount differs", both payments side by side, refund instructions (PayFast dashboard → Transactions → the extra `pf_payment_id` → Refund; R2 ex VAT), "Mark resolved" with a note. The dashboard shows "Payments: N flagged" when any are open.
- **Report** — per option for a date range: attempts started, paid, share paid, total paid, PayFast fees; under it the paid orders with "paid with", fee and net, each expandable to its attempts; CSV download.

## Why the non-obvious decisions
- **The browser sends a key, the server owns the code.** A request with a made-up code can't even be expressed: `begin-payment` has no code field and the signer ignores the payload's `payment_method`.
- **`m_payment_id` stays the order reference; the attempt rides in `custom_str3`.** Today's ITN matching (unique `orders.m_payment_id`) and every existing caller are untouched; the attempt match is purely additive.
- **Amount mismatches flag, never refuse.** `orders.total` is written by the browser and can be edited later; real orders already show legitimate differences. Refusing would drop real money. Flag, complete, let an admin look.
- **No valid-host (PayFast IP) check, on purpose.** Netlify's client-IP header and PayFast's IP ranges both move; the passphrase-signed body plus the `/eng/query/validate` confirmation cover forgery. Don't "fix" this without reading the plan §4.4.
- **Server confirmation only while the picker is on**, so switching the picker off returns the ITN to byte-for-byte today's behaviour.
- **"Last used" for accounts comes from paid attempts, not a profile column** — one source of truth, and it can only ever be an option that actually paid.
- **No new switch for the checkout re-layout**: dual-rendering the 6,500-line page would duplicate it; the revamp changes no money logic. Rollback = redeploy the previous commit.
- **A token is only requested for a new card** (`subscription_type=2` only for Card → Add a new card with "Save this card" on) — never for Capitec, EFT or wallets.

## Gotchas / before touching
- **PayFast is strict about field order.** If you add a field to the signer, put it in PayFast's documented position and keep empty fields out of both the string and the form. A wrong position shows PayFast's "signature mismatch" page immediately — always check on the sandbox first.
- `PAYFAST_SANDBOX` **defaults to sandbox when unset** in the signer. Production must have it set to `false`; deploy previews should have it `true` with sandbox merchant credentials so QA never touches the live account.
- The sandbox has one test wallet. It proves the signature, redirect, return, cancel and ITN — **not** that Capitec Pay / EFT / card / Apple Pay / Google Pay open correctly. Each method needs one small live payment (then a refund) before it is switched on for everyone.
- **Deploy previews and production share one Supabase project**, so `site_settings.payments.enabled` is global — there is no "on for the preview only" or "admins only". Run picker-on QA on a preview *before* the picker code is on main (production code ignores the key until then) and switch it off again before merging. A sandbox COMPLETE on a preview writes a real paid order into the live database (store sees it, a delivery is created): use a cheap Umzila-store item and mark it refunded straight after.
- Switch an option on only if the method is **enabled on Umzila's PayFast account**; otherwise PayFast shows the buyer an error page.
- `cc` vs `dc`: the Card option uses `cc`. If the live debit-card test is refused, add a second option "Debit card" with code `dc` in the admin — no code change.
- There is exactly one catch-all (code `null`). The admin screen enforces it; if you edit the JSON by hand, keep it.
- `site_settings.payments` is read on page load. An admin change reaches a buyer who already has checkout open only when they press Pay (server refusal → list reloads).
- Saved-card charges go through `begin-payment` → the existing `charge-payfast-token.handler`; there is no ITN for them, so `begin-payment` marks that attempt paid itself.
- The success page still empties the cart optimistically when polling gives up (pre-existing behaviour) — the order is paid only by the ITN (P12); opening the return page by hand marks nothing paid.
- Don't add another payment-verification path. Paid = `orders.payment_status='paid'` set by `completeOrderPayment` (ITN, saved card, R0) only.
- Seller enrolment payments use `checkout-cancel.html` without an order reference — keep the message card working for them.

## Pre-switch-on checklist (founder)
1. PayFast dashboard → Settings → Payment methods: enable Card, Capitec Pay, Instant EFT, Apple Pay, Google Pay (Samsung Pay optional). Only switch on in Admin → Payments the methods that are enabled there.
2. Netlify → Environment variables → **deploy-preview context**: `PAYFAST_SANDBOX=true` and the sandbox `PAYFAST_MERCHANT_ID / KEY / PASSPHRASE`. Production: confirm `PAYFAST_SANDBOX=false`, `SITE_BASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`.
3. Run the sandbox QA in `docs/qa-payment-picker.e2e.js` on a deploy preview *before merging* (the switch is shared with production — see Gotchas), then switch it off again.
4. Merge with the picker **off**; watch two days of live orders through the new checkout.
5. Live test each method once (R5–R10, refund in PayFast afterwards, R2 ex VAT each) — steps in `docs/qa-payment-picker.e2e.js` (LIVE section). Check Admin → Payments → Report shows each attempt paid with its fee.
6. Switch "Payment picker on" at a quiet time; after a week read the report and reorder options if the numbers say so.
