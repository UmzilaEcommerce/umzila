# Delivery timeslots

Customers pick a delivery window (a "run": one slot on one date, e.g. 12:00–13:00 on 16 Nov) at checkout. The one promise that must always be true: **order before the cut-off and the order arrives inside the window.** Everything is behind one switch, `site_settings` key `timeslots` → `enabled` (**Admin → Delivery → Delivery Times**). **While it is false the whole system is inert**: the order triggers return the row untouched (client-supplied slot columns are nulled), `timeslot_runs_for_cart` returns `{enabled:false}`, the job exits after one settings read, dispatch takes no timeslot branch, and checkout/pages/emails show today's behaviour. Design: `docs/plans/delivery-timeslots-plan.md` (the FOUNDER DECISIONS block at its top overrides the rest); brief: the founder's "delivery timeslots developer brief" (2026-11-14). Built 2026-11-14 by five workstreams (A DB/server, B checkout, C admin, D stores/emails/wording, E dispatch), reviewed and fixed 2026-11-15.

## The promise, in one run (defaults: cut-off 15 min, grace 5 min)
12:00–13:00 run. Until 11:45 customers can choose it and pay. 11:45 = cut-off: checkout stops offering it, the store is told to start preparing (email + dashboard), admins get the same summary, dispatch releases the run's deliveries to riders. 11:45–11:50 = payment grace: a payment started before 11:45 that lands by 11:50 is still in the run (store + admins get "Add to the 12:00 run"). Later than that, the order moves to the next open run (R12) or is flagged "needs attention" (R13). The software enforces only the cut-off and the grace end; the other times shape wording.

## Where the rules live
**The database is the single source of truth.** `timeslot_open_runs(p_seller_ids uuid[], p_at timestamptz)` answers "which runs can this cart order for at time T" (service-role only; time is an input so it is testable at 11:44 / 11:45 / 11:51). States, first match wins: `off` (slot inactive), `paused` (exception with slot_id null for the date), `skipped` (exception for the slot + date), `closed` (T ≥ cut-off, **or** the run's summary was already sent — so a cut-off change never reopens a run that stores were already told about), `store_closed` (a non-house goods store in the cart is shut at the cut-off or at the window start — stores with no `seller_availability` rows count as always open, founder decision 3), `full` (optional `max_orders`, R16), `open`. Cut-off = window start − `cutoff_minutes`; exactly the cut-off moment is closed (R7). Days: today .. today + `days_ahead`, in Africa/Johannesburg (R21). Settings come from `timeslot_settings()` (defaults merged: cutoff 15, grace 5, days_ahead 1, busy 6).

Three triggers on `orders` use it, so no PayFast function was edited:
1. `trg_timeslot_guard_insert` (BEFORE INSERT) — R9/R10, atomic check-and-create at the Pay tap (the existing browser insert into `orders`). Applies only to `pending_payment` orders with at least one non-service, non-house item not covered by a self-arranged store (`timeslot_goods_sellers`, `timeslot_self_arranged` — same item resolution as `create_delivery_on_payment`). Missing slot → `TIMESLOT_REQUIRED`; run not open → `TIMESLOT_CLOSED` with `DETAIL` json `{reason, closed_at, window_start, window_end, next_open{slot_id,run_date,window_start,window_end,cutoff_at}|null}` (PostgREST surfaces it as `error.details`). On success the server stamps `slot_window_start/end` (copy as sold) and `slot_pay_pressed_at = now()`; client values for those are ignored. Locks the slot row (`for update`) so `max_orders` cannot be beaten by two simultaneous pays. Priority fee is left as the client priced it (founder decision 2).
2. `trg_timeslot_guard_update` (BEFORE UPDATE) — anon/authenticated JWTs cannot change `slot_*` columns (`SLOT_COLUMNS_LOCKED`); admin functions set `umzila.slot_write` for the transaction.
3. `trg_timeslot_on_paid` (BEFORE UPDATE OF order_status, WHEN new = 'paid' and old is not 'paid' and slot_id is not null) — R11/R12/R13 using `paid_at` (set by `completeOrderPayment` in the same update). Pressed before the cut-off AND paid ≤ cut-off + grace → stays. Else moves to the next `open` run with a later window (`delivery_run_moves` row, reason `late_payment`, actor `system`) or, with none, `slot_needs_attention = true` (move row with null `to_*`). The WHEN clause is why a duplicate ITN changes nothing (`completeOrderPayment` also returns early on `alreadyPaid`); it runs BEFORE the AFTER triggers so `create_delivery_on_payment` sees the final run. Also upserts the `delivery_runs` row lazily.

`timeslot_now()` lets service/postgres sessions override the clock with `set_config('umzila.now', ...)` for tests; anon/authenticated always get `now()`.

## Tables
`delivery_slots` (start/end time SAST, `days smallint[]` 0=Sun…6=Sat, `active`, `max_orders`; triggers `SLOT_OVERLAP` on insert/update — checked against all slots, on or off — and `SLOT_HAS_PAID_ORDERS` on delete when paid future orders exist; seeded 12–13, 14–15, 16–17, 18–19 every day, R2), `delivery_slot_exceptions` (run_date + slot_id; slot_id null = whole date paused, R5), `delivery_runs` (per run: `summary_claimed_at/summary_sent_at/summary_sent_to uuid[]/busy_alert_sent_at/late_minutes/late_sent_at`; created lazily on the first paid order or by an admin move), `delivery_run_moves` (every move: from/to window, `reason` late_payment|admin|admin_stop|refund, `actor_type` system|admin, `actor_id`, `customer_emailed_at`), `admin_alert_emails` (admin-only alert recipients; the job falls back to env `ADMIN_EMAILS` only when the table has no active row — founder decision 4), plus `orders.slot_id, slot_run_date, slot_window_start, slot_window_end, slot_pay_pressed_at, slot_needs_attention` (partial index on slot_id, slot_run_date). "Time payment confirmed" = `orders.paid_at`. The cut-off is never stored: always `slot_window_start − cutoff_minutes` (brief: a cut-off change applies to every run whose cut-off has not passed). A slot edit never changes an order's sold window.

RLS: slots + exceptions readable by everyone, written by admins (`timeslot_is_admin()`); `delivery_runs` staff read; `delivery_run_moves` staff read + the order's owner (uid or `my_verified_email()`); `admin_alert_emails` admins only, revoked from anon; all writes to runs/moves happen in SECURITY DEFINER functions or the service role.

## Server code
- `netlify/functions/lib/timeslots.js`: `runTick(supabase, siteUrl)` (the job body), `timeslotAfterPaid(supabase, orderId, siteUrl)` (called from `complete-order-payment.js` right after payment, guarded, no-op without a run), `adminAlertEmails`, `sellerRecipients` (`sellers.email` + owner + `seller_members`, same as the new-order email), `loadRunOrders` (R14: paid, not refunded/cancelled, not needs-attention), `itemTotals`, `logOnce` (one `notification_log` row per order+event, the existing unique index), `sendMail` (Resend, `mailFrom('Umzila','orders')` for customers/admins, `mailFrom('Umzila Sellers','sellers')` for stores — transactional only).
- `timeslot-tick.js`, scheduled every minute in `netlify.toml` (exits after one settings read while off). Steps, each claim-first and idempotent: (1) **cut-off summaries** — for every `delivery_runs` row with `summary_sent_at` null whose cut-off has passed: claim `summary_claimed_at` (a stale claim older than 3 min is retaken after a crash), re-load the paid orders; none → `summary_sent_at` set, nothing sent; else per store not yet in `summary_sent_to`: email (`storeRunSummary`: totals per item+size first, then the orders one by one) + `seller_notifications` type `run_summary` (metadata `{slot_id, run_date, totals, window_start, window_end}`), append the store id; then one admin summary (`adminRunSummary`, all stores + "Umzila stock" house items; sentinel uuid in `summary_sent_to`); `summary_sent_at` last. A crash retries only unsent parties, so a store never gets two summaries and none is lost. (2) **per order** (paid in the last 36 h with a run, plus any order with an unsent move row): "Add to the 12:00 run" when `paid_at` is inside the grace window **and after the summary was claimed** (earlier payments are already inside the summary) — once per order via `TS_GRACE_ADD`, store email + `seller_notifications` type `run_addition` (metadata `{slot_id, run_date, totals, order_number}`) + admin email; run-changed mail (`customerRunChanged`: old window, new window, "cancel for a full refund until <new cut-off> — reply or WhatsApp") by claiming `delivery_run_moves.customer_emailed_at`; needs-attention mails (customer "Umzila will contact you" + admin) once via `TS_NEEDS_ATTENTION`. (3) **busy alert** — paid count ≥ `busy_alert_at` → claim `busy_alert_sent_at`, one admin email per run. The payment hook runs steps 2–3 for the just-paid order immediately, so the busy alert goes at the 6th payment and the grace add within seconds; the tick is the safety net.
- `timeslot-admin.js` (POST, admin Bearer token checked against `admins`): `tick` (run the job now — the admin page calls it after a move so the email goes at once), `mark_refund` (order_status `refunded`, delivery → CANCELLED through `transitionDelivery` where the state machine allows it, move row reason `refund`, `customerRefunded` email; **the money is refunded by hand in PayFast**), `running_late` (minutes → `customerRunningLate` to every paid customer in the run, stamps `delivery_runs.late_minutes/late_sent_at`).
- `order-status.js` returns `run: { run_date, window_start, window_end, cutoff_at, needs_attention, moved_from }` for paid orders with a slot (window null when needs attention).
- `lib/timeslot-mail.js`: pure builders returning `{subject, html}` on `notify.js`'s `emailShell`: `storeRunSummary, adminRunSummary, storeRunAddition, adminRunAddition, customerRunChanged, customerNeedsAttention, adminNeedsAttention, adminBusy, customerRunningLate, customerRefunded`, plus the shared SAST formatters (`hhmm`, `dayWord`, `windowLabel`) that `complete-order-payment.js` reuses for the confirmation subject ("Order confirmed — arriving today 12:00 to 13:00 — UMZILA-…") and first line; the closed-store note is suppressed for slot orders (R18 guarantees the store is open for the run). The confirmation email's `require` of this lib is wrapped in a try so nothing here can ever block a PayFast completion.

## RPCs for pages
`timeslot_public_config()` → `{enabled, cutoff_minutes, grace_minutes, days_ahead, busy_alert_at, server_now}` (seller dashboard, profile); `timeslot_runs_for_cart(uuid[])` → `{enabled, server_now, cutoff_minutes, grace_minutes, runs[{slot_id, run_date, window_start, window_end, cutoff_at, state, blocking_store}], next_open}` — every candidate run so the page can say why nothing is open; `get_run_sheet(from, to)` (staff) → jsonb array of runs `{slot_id, run_date, window_start, window_end, cutoff_at, state taking_orders|preparing|out_for_delivery|done|skipped|paused|off, paid_count, busy, summary_sent_at, late_minutes, needs_attention_count, stores[{seller_id, shop_name ("Umzila stock" for house), orders[{order_id, order_number, customer_name, customer_phone, address, items[{name,size,qty}], delivery_status, needs_attention, moved_from}]}]}`; `admin_affected_orders(slot_id?, run_date?)` (either may be null); `admin_runs_for_order(order_id)` (jsonb array, every state — the admin may knowingly pick a closed one); `admin_move_order_run(order, slot, date, reason)` (paid orders only, writes the window from the slot, clears needs-attention, move row with `actor_id`, upserts `delivery_runs`; the run-changed email follows via the tick). `get_delivery_tracking` gained `slot_window_start, slot_window_end, slot_cutoff_at, slot_needs_attention`; `get_ops_board` deliveries gained `run_window_start/end`.

## Checkout (checkout.html, workstream B)
Everything sits behind `tsActive()` = switch on AND the cart has goods from a non-house store. The picker replaces the "Delivery target: about N min" strip (`#estimatedDeliveryTime` → `tsRenderPicker`): runs grouped by day, earliest open selected, "Order in the next N min" under 60 min / "Order by 13:45" otherwise, red "Pay in the next 4 min to get this time." inside 5 min, "Deliveries are closed for today. The next delivery time is tomorrow, 12:00 to 13:00." when nothing is open today, a store-closed / nothing-open message with Pay disabled (R9), and the "Order by 11:45 and get it between 12:00 and 13:00." note. Time comes only from the RPC's `server_now` anchored to `performance.now()` (R21); the list refreshes every 30 s, when a selected run crosses its cut-off (the page says so and selects the next run), when the tab becomes visible, and when the cart's store set changes. The Pay button reads "Pay R142 · Today 12:00 to 13:00". `orderData` carries `slot_id` + `slot_run_date`; a `TIMESLOT_CLOSED`/`TIMESLOT_REQUIRED` insert error shows "12:00 to 13:00 closed at 11:45. The next delivery time is 14:00 to 15:00.", selects that run, re-enables Pay and **stops** — the buyer must press Pay again (never switch and charge in one go). The closed-store popup is skipped while active (R18 means a run is only offered when every store is open for it). Priority stays, with the help text "Delivered first in your delivery window" (founder decision 2). Services-only carts never see a picker (R19). With the switch off (or the RPC failing) the page is byte-for-byte today's.

## Admin console (admin.html → Delivery → Delivery Times, timeslots-admin.js, workstream C)
Phone-first (real CSS classes, bottom-sheet modals ≤640 px). Top: the master switch (confirm dialog; advises switching on after the last cut-off of the day). Then: the affected-orders warning (after switching a slot off, changing its days, skipping a run or pausing a date — lists paid orders in the stopped runs with Move / Mark for refund per order and for all), the needs-attention card (from the run sheet + a direct query so orders outside today/tomorrow show too), the run sheet for today and tomorrow ("Run cut-off job now" + refresh; per run: window, cut-off, state pill, paid count, Busy pill, orders grouped by store with tel: links, address, items, moved-from, Move / Refund buttons, "Running late" with a minutes prompt; "No orders" when empty), slots (window, computed cut-off, day chips, on/off switch, max orders, Edit / Delete — delete of a slot with paid future orders offers "Switch off instead"), date controls (skip one run, pause a date, list with Remove and an Undo), settings (validated ranges; a cut-off change while live asks for confirmation), alert emails (add — via `UmzilaInput.ok` — switch off, remove). Writes go through admin RLS, the SECURITY DEFINER RPCs and `timeslot-admin.js`; the page auto-refreshes every minute when idle.

## Stores and customers (workstream D)
- **Seller dashboard**: active orders with a run are grouped under a header "12:00 run · start preparing at 11:45 · collection about 12:00" (+ date, window, count); before the cut-off the group is marked **Do not prepare yet** and the Mark Ready button is hidden (and refused if forced); from the cut-off **Prepare now** + the button. A "Run summary — total to prepare" card appears from the cut-off, using the totals the cut-off summary stored in `seller_notifications` (else worked out from the orders) plus any "Add to the run" lines. Needs-attention orders sit in a "Waiting for a delivery time" group (never prepare). Orders without a run (switch off, services, older orders, manual ORD-… orders) render exactly as before under "Other orders". The clock is `timeslot_public_config().server_now`-anchored; a 30-s timer re-renders when a run crosses its cut-off. `isPastOrder` is unchanged (a refunded order drops out as before).
- **Customer wording** (slot orders only; everything else keeps today's text): confirmation page (`checkout-success.html` from `order-status.run`) "Order confirmed. Arriving today between 12:00 and 13:00." / moved note with the cancel-until time / "Umzila will contact you shortly"; `track.html` and the `index.html` widget map (delivery status, window, cut-off, now) → Confirmed ("Arriving today between…") → Preparing (from the cut-off, "The store is preparing your order. Arriving between…") → Out for delivery ("Your order is on the way. It arrives by 13:00.") → Delivered (existing); `profile.html` badge "Confirmed · 12:00–13:00" / "Preparing · …". The closed-store "made when it opens" wording is never shown for a slot order.
- **Emails**: confirmation (window in subject + first line), run changed, needs attention (customer + admin), store summary, store/admin "Add to the run", busy, running late, refunded — see Server code.

## Dispatch (workstream E) — see docs/systems/ops-panels.md "Delivery timeslots and dispatch"
A delivery whose order has a run is held (`waiting_for_run`) until the cut-off on every offer path (`lib/dispatch.js isHeldForRun`), the heartbeat sweep pages past held deliveries, same-run orders wait for a run-mate's pending fresh-trip offer and then batch onto it, and `lib/route-insertion.js` plans run-mates in "run mode" (no 8-min / 60-min protection among them, priority run-mates first, 5-order cap unchanged). Admin manual redispatch is held too.

## Security notes
- The review found a pre-existing hole unrelated to slots: the policy "Users can update their own orders" had no column limits, so a signed-in buyer could PATCH `order_status='paid'` on their own pending order (the sync trigger then set `payment_status='paid'` and the delivery / order_items triggers fired), or edit totals before paying. Fixed by the BEFORE UPDATE trigger `orders_client_update_guard` (SECURITY INVOKER: it only sees DIRECT anon/authenticated writes; SECURITY DEFINER RPCs, triggers and the service role pass; staff via `timeslot_is_staff()` pass): customers may change only `order_status` (Pending/Packaging/Fulfilled/Delivered/Returned, never from `pending_payment`) and `notes` — `ORDER_COLUMNS_LOCKED` / `ORDER_STATUS_LOCKED` otherwise. The customer DELETE policy now covers unpaid `pending_payment` rows only.
- `timeslot_open_runs`, `timeslot_store_open_at`, `timeslot_goods_sellers`, `timeslot_self_arranged`, `timeslot_settings`, `timeslot_enabled`, `timeslot_cutoff_at` are not callable over REST; `timeslot_is_admin/_staff` are (RLS policies evaluate them as the signed-in user). Admin RPCs check `timeslot_is_admin()` inside; `get_run_sheet` checks staff. `timeslot-admin.js` checks the Bearer token against `admins`.
- The price columns of an order are still written by the browser at insert (pre-existing checkout design; `validate-cart.js` is the pricing authority before that) — out of this build's scope.

## Gotchas / before touching
- Moving an order by hand into a run whose summary was already sent produces no automatic "Add to run" message (staff phone the store, as the brief says).
- A summary retried after a crash re-stamps `summary_claimed_at`; a payment landing in that gap could in theory get both a summary line and an addition mail.
- A store with no opening hours is treated as always open: enter hours for every goods store before switching on.
- Self-arranged-radius stores and services/bookings/house-only carts have no slot; manual logistics orders (not `pending_payment`) are never touched by the insert trigger.
- Needs-attention orders still carry the slot they missed: the run sheet lists them first under that run; `loadRunOrders` (summaries, running late) leaves them out; `admin_move_order_run` clears the flag.
- `runTick` queries once per recent paid order each minute — fine at today's volume; batch it before hundreds of orders a day.
- Tests: all rule SQL is time-injected (`timeslot_open_runs(ids, '… 11:44+02')`, `set_config('umzila.now', …)`, explicit `paid_at`) inside DO blocks that `raise` at the end so nothing is left behind. SQL sources in `docs/plans/sql/` (1 schema, 2 rules, 3 reads, 4 review fixes).

## Pre-switch-on checklist (founder)
1. Deploy preview with PayFast sandbox and the switch ON there only (a Supabase branch, or `netlify dev` against a dev project — never flip the live row for testing). Run the brief's acceptance tests by hand: 11:44 list/select, 11:45 switch, Pay refused at 11:46 and the message, paid in grace → "Add to the run" once, paid late → moved + "Run changed" email + a working cancel (Mark for refund), same ITN twice, 17:50 only tomorrow, every slot off → Pay disabled, 6th paid order → one busy email, store summary once with correct totals (and nothing for a store with no orders), skip/pause + Move, slot edit keeps the sold window, device clock 3 h wrong, service-only cart no picker, `grep` for "driver is on it"-style wording on a slot order.
2. Enter opening hours (seller dashboard → Hours, or admin) for every goods store, or accept that stores without hours are offered every run.
3. Add the admin alert addresses in Delivery Times → Alert emails (or confirm env `ADMIN_EMAILS`).
4. Check the slots and settings in Delivery Times (default 12/14/16/18, cut-off 15, grace 5, days ahead 1, busy 6).
5. Confirm `RESEND_API_KEY`, `SITE_BASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` are set on the production site (the tick runs there every minute) and that the `timeslot-tick` schedule appears in Netlify → Functions after deploy.
6. Flip the switch in Admin → Delivery Times after the last cut-off of the day (the confirm dialog says so), then watch the run sheet and the alert inbox for every run in week one and write down the real times (store ready, driver left, last order arrived) to tune the settings.
